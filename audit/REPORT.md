Audit of the current Deniqwears working tree, 13 September 2026

The application has release-blocking payment, customer-data exposure, inventory, and storefront defects. This review covers the working tree, including its substantial pre-existing uncommitted changes; it is not limited to the last commit or diff. Application source was not changed. The added audit files contain the report and isolated reproductions.

Priority means: **P1** — resolve before accepting real orders or deploying this version; **P2** — functional, correctness, security, or operational issue requiring a fix; **P3** — lower-impact quality or completeness issue. Dependency advisory severity is reported separately from application priority.

Verification performed:

- Existing suite: 28 tests passed in the initial run; the remaining 8 database tests passed outside the filesystem/network sandbox. The initial PostgreSQL failures were environmental. These were run before the user clarified their Bun preference; subsequent commands use Bun.
- `bun run test --config audit/vitest.config.ts`: **21/21 passed**. These tests deliberately assert the currently broken behavior; a pass confirms a defect, not application correctness. All database/payment boundaries are mocked. No real payments or emails are sent by these reproductions.
- `bunx prisma validate`: schema is valid; Prisma warns that the `package.json#prisma` configuration is deprecated for Prisma 7.
- `bunx tsc --noEmit`: fails with two TS2540 errors in `tests/config.test.ts`.
- `bun run lint`: **0 errors, 67 warnings**, also after adding the audit reproductions.
- `bun run build --webpack`: application compiled, then failed TypeScript checking on those same two errors. The default Turbopack build hit Google-font network restrictions and, on retry, a port-binding restriction. Those environment failures are not counted as application bugs.
- `bun audit --json`: two distinct advisories across three package entries; details below.
- Read the installed Next.js 16.3.5 route-handler and `after()` guidance, and checked relevant upstream documentation for query freshness and refund semantics.

1. **[P1] A payment for one order can pay another order.** [server/payment/service.ts:60](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:60), [payment verification route:18](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/src/app/api/payments/verify/route.ts:18). The public endpoint accepts an independent `reference` and `orderId`; the service never compares the reference with the order's stored reference, checks provider metadata/client reference, or ensures a captured transaction is assigned to only one order. A successful reference for order A can mark same-price order B paid, and can be reused across multiple orders. The database has no unique constraint on `paymentId`. **Reproduced.** Bind provider, stored reference, order identity and transaction identity, then atomically claim the payment once.

2. **[P1] Unauthenticated, enumerable order lookup exposes customer details and payment identifiers.** [order GET route:9](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/src/app/api/orders/[id]/route.ts:9), [server/db.ts:378](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/db.ts:378). `GET /api/orders/DNQ-12345` returns the full order without authentication or a signed guest token. `getOrderById` also accepts the five-digit public order number; an attacker need not guess a CUID. Responses contain names, email, telephone, address, payment reference/ID, timeline, and idempotency key. The verification endpoint also returns a paid order before checking its supplied reference. **Unauthenticated response reproduced; enumeration follows from the lookup and number generator.** Require authorized access or a cryptographically strong scoped guest token, and return a minimal customer-safe response.

3. **[P1] Retrying an idempotency key restarts payment, including for already-paid orders.** [checkout route:39](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/src/app/api/checkout/route.ts:39), [server/payment/service.ts:46](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:46). A repeated key calls `initializePayment` again, overwrites the payment reference/method and sets `PAYMENT_PROCESSING` regardless of the existing status. A retry can reopen a paid/refunded/fulfilled order or orphan an earlier gateway session; a later webhook for the overwritten reference cannot find it. The branch also does not check that the new payload belongs to the original customer/cart. Combined with finding 2, an exposed key can be used to mutate another order. Return the existing outcome/session for an identical request, reject conflicting payloads, and model new payment attempts explicitly.

4. **[P1] Checkout can sell more stock than exists.** [checkout route:52](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/src/app/api/checkout/route.ts:52), [server/db.ts:469](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/db.ts:469). Stock is checked before order creation but never reserved. Concurrent checkouts can both pay for the last unit. A single request can also repeat the same variant on multiple lines, each individually passing the stock check. At payment completion, the decrement condition is `stock >= 0`, not `stock >= quantity`; negative inventory is then clamped to zero, concealing the oversell while accepting payment. **Repeated-line checkout and unsafe decrement reproduced.** Aggregate quantities per variant and use atomic stock reservation/conditional decrements with an explicit shortage policy.

5. **[P1] Concurrent payment confirmations decrement inventory twice.** [server/db.ts:462](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/db.ts:462), [server/payment/service.ts:66](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:66). Both the service and `updateOrderStatus` read status before entering the transaction. A webhook and browser callback can both observe an unpaid order and independently subtract its quantity, add paid timeline entries, and schedule confirmation emails. A transaction around the writes does not make the prior read atomic. **Reproduced with two callers observing the same unpaid row.** Lock/conditionally transition the order inside the transaction and only let the winning transition perform stock and notification effects.

6. **[P1] Order status changes have no valid-transition enforcement.** [server/payment/service.ts:66](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:66), [status route:35](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/src/app/api/admin/orders/[id]/status/route.ts:35), [server/db.ts:456](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/db.ts:456). Verification short-circuits only `PAID` and `FULFILLED`, so replaying a successful charge on a `REFUNDED`, `PARTIALLY_REFUNDED`, or cancelled order writes `PAID` again. The admin endpoint accepts any enum transition, including fulfilment without payment or `REFUNDED` without issuing/recording a refund. Transitions do not consistently reconcile inventory or financial fields. **Refund-to-paid replay reproduced.** Enforce a state machine; separate payment state, fulfilment state, refund records, and stock-return actions where needed.

7. **[P1] Pending or unsuccessful refunds can be recorded as completed refunds.** [server/payment/service.ts:153](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:153), [providers.ts:309](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/providers.ts:309). The service ignores `RefundResult.success`, `status`, and returned amount, increments refunded funds, changes the order status, and triggers the refund email. Stripe explicitly returns `pending`; the showroom provider returns `pending` with zero funds moved. Paystack/Flutterwave adapters also flatten accepted requests to `processed`. **Pending-result behavior reproduced.** Store the actual gateway refund result and reconcile completion/failure before treating it as settled. Both [Stripe](https://docs.stripe.com/refunds) and [Paystack](https://paystack.com/docs/payments/refunds/) document pending/failed refund states.

8. **[P1] Refunds lack durable idempotency and concurrency control.** [server/payment/service.ts:139](/Users/oneremitengineeringiv/Documents/freelance/deniqwears/server/payment/service.ts:139). Two requests can read the same remaining balance, both call the gateway and both increment `refundedInKobo`. A successful gateway refund followed by a database/logging failure returns an error without a durable refund record; retrying can submit another refund. The balance update, status change and audit log are separate operations. **Concurrent use of the same remaining balance reproduced; whether a gateway permits both refunds depends on its own limits.** Persist a unique refund operation and reserved refundable balance before submitting, pass gateway idempotency where supported, and reconcile uncertain outcomes.
